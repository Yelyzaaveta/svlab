# Лабораторна робота 5. HTTP API та DynamoDB на osls

Варіант 2 — м'яке видалення.

## Частина A. Модель даних

### 1. Патерни доступу

1. Створити організацію.
2. Додати користувача до організації.
3. Оновити організацію.
4. Оновити користувача.
5. Отримати організацію з користувачами.
6. Перевірити, чи зайнятий email.
7. М'яко видалити користувача (варіант 2).

### 2. Запити і ключі

| Патерн | Запит | Ключ (PK / SK) |
|---|---|---|
| Створити організацію | TransactWriteItems | `ORG#<orgId>` / `ORG#<orgId>` + `ORGNAME#<name>` / `LOCK` |
| Додати користувача | TransactWriteItems | `ORG#<orgId>` / `USER#<userId>` + `EMAIL#<email>` / `LOCK` |
| Оновити організацію | UpdateItem | `ORG#<orgId>` / `ORG#<orgId>` |
| Оновити користувача | UpdateItem | `ORG#<orgId>` / `USER#<userId>` |
| Отримати організацію з користувачами | Query | `PK = ORG#<orgId>` |
| Перевірити, чи зайнятий email | GetItem | `EMAIL#<email>` / `LOCK` |
| М'яко видалити користувача | TransactWriteItems | `ORG#<orgId>` / `USER#<userId>` + `EMAIL#<email>` / `LOCK` |

Жоден патерн не використовує Scan.

### 3. Таблиця

| Елемент | PK | SK | Атрибути |
|---|---|---|---|
| Організація | `ORG#<orgId>` | `ORG#<orgId>` | name, description, version, createdAt |
| Користувач | `ORG#<orgId>` | `USER#<userId>` | userId, name, email, version, createdAt, deletedAt, ttl |
| Замок назви | `ORGNAME#<name>` | `LOCK` | orgId |
| Замок email | `EMAIL#<email>` | `LOCK` | orgId, userId |

### Обґрунтування

**Підхід.** Одна таблиця з ключами PK і SK. Організація та її користувачі мають однаковий PK, тому їх можна отримати одним запитом Query. Замки для назви й email лежать у тій самій таблиці, тому їх можна записати в одній транзакції з основним елементом.

**Ключі.** PK — ключ розділу, SK — ключ сортування. Префікси (`ORG#`, `USER#`, `ORGNAME#`, `EMAIL#`) показують, який тип елемента лежить у рядку. Замки з SK = `LOCK` потрібні для унікальності назви організації та email без Scan.

**Індекси.** Індекси не потрібні: усі патерни виконуються за первинним ключем таблиці.

## Варіант 2. М'яке видалення

`DELETE /organizations/{orgId}/users/{userId}` не видаляє елемент користувача, а однією транзакцією:

1. проставляє `deletedAt` (час видалення) і `ttl` (epoch-секунди, через 30 днів) з умовою `attribute_exists(PK) AND attribute_not_exists(deletedAt)`;
2. видаляє замок `EMAIL#<email>` / `LOCK` з умовою, що він належить саме цьому користувачу.

Тому видалений користувач:

- не повертається в `GET /organizations/{orgId}` (фільтр за `deletedAt`);
- не блокує повторну реєстрацію того самого email: замок звільнено в тій самій транзакції, тож стану «користувач видалений, а email зайнятий» не буває;
- не оновлюється через PUT (404), повторний DELETE теж дає 404.

TTL увімкнено для таблиці у `serverless.yml` через `TimeToLiveSpecification` з атрибутом `ttl`.

### Чому TTL не гарантує негайного видалення

TTL — це фоновий процес DynamoDB, а не тригер. Після того як час у `ttl` минув, елемент видаляється не одразу, а зазвичай протягом кількох днів; точного терміну AWS не гарантує. Увесь цей час прострочений елемент і далі повертається в Query та GetItem. Тому застосунок не може покладатися на TTL як на факт видалення: ознакою видалення є `deletedAt`, і код сам відфільтровує такі елементи. TTL лише безкоштовно прибирає старі записи з таблиці згодом.
